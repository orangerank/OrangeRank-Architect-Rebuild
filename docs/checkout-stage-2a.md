## Pending assessment and retry model

Redis stores one durable JSON pending record per randomly generated UUID v4 `intake_submission_id`. Record includes all validated intake values, `PENDING` payment status, `NEW` assessment status, ISO created date, versions, Assessment ID and Stripe Session ID. No ledger or fulfillment is created. Redis Lua atomically checks the submission key before incrementing the per-date/business collision counter and saving the pending record. IDs use America/Chicago date and a normalized uppercase ASCII business slug (max 60 characters, fallback BUSINESS); collisions suffix -2, -3, etc. Records/counters have no automatic expiry to avoid losing references or recycling IDs. Owner must establish retention/deletion and access policy before real data intake. Provision a Redis service with durable storage/backups; never an ephemeral process map or local disk. Do not manually clear counters.

Browser stores only a submission UUID and input hash in sessionStorage, not raw intake. This is a retry hint, never the authoritative record. Repeated identical submissions in a tab reuse the ID; changed intake starts a new submission. Server binds the ID to a canonical input fingerprint and rejects mismatches. No cross-device deduplication of independent intentional submissions is claimed. The Stripe idempotency key is `or-checkout-<UUID>`, with stable parameters reconstructed from the saved record. If Stripe succeeds and Redis persistence fails, retry recovers the same Session using that key. Session IDs already saved are retrieved, not recreated. Unresolved creation older than 20 hours is refused rather than risking reuse after Stripe's 24-hour idempotency window; expired/completed sessions require support, not automatic new checkout. See https://docs.stripe.com/api/idempotent_requests and https://docs.stripe.com/api/checkout/sessions/create.

Checkout uses the configured active non-live one-time USD 14900 Price. Metadata on Session and PaymentIntent contains assessment_id, business_name, website, customer_email, product=orangerank_assessment_v1, ledger_version=ControlLedger-V1.0, methodology_version=PRODUCTION-v1-LOCKED, report_template_version=V1.3, intake_submission_id. Notes/phone/services/competitors are not sent in metadata. No secret or payment details in metadata. Price and return origin are environment controlled, not customer supplied.

API validates field types/lengths, required fields, allowed category/state, URLs, email and strict boolean terms acceptance. Same-origin check, JSON-only requests, request-size limit, per-IP rate limit and opaque UUID record references. Cancel uses an HttpOnly SameSite cookie to resume the saved open session without exposing intake. Generic success page cannot assert payment or authorize work. Request/provider errors are not logged or exposed.
