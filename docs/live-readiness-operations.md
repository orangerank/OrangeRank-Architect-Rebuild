# Readiness implementation, not activation

This document supersedes the earlier test-only code/guard descriptions in production-cutover-readiness.md and checkout-stage-2a.md.
No credentials or configuration were changed. New checkout requires both ORANGERANK_CHECKOUT_ENABLED=true and ORANGERANK_CHECKOUT_RELEASE_APPROVED=true. Both remain disabled by default. Explicit ORANGERANK_STRIPE_MODE=test is required for Preview/local; Production requires live plus ORANGERANK_LIVE_APPROVED=true. Missing mode means fail closed, including existing Preview. Stripe secret/Price/session/intent/event modes must match. Price remains active one-time USD149. Webhook reconciliation does not depend on either checkout-enable flag, but requires mode, matching Stripe credentials and webhook secret.

Separate Stripe key/Price/signing secret and Redis DB per environment. Canonical future Production webhook https://www.getorangerank.com/api/stripe/webhook for checkout.session.completed and checkout.session.async_payment_succeeded. No endpoint/configuration was created. Do not activate until separate approval, legal/privacy and operational review.

Atomic payment-owner key or:payment-owner:<PaymentIntent> binds one assessment permanently; no expiry. Existing confirmed records lacking ownership keys return OWNERSHIP_REVIEW without changes. Historical duplicates remain financially recorded but cannot pass dispatch without payment_ownership_verified and identity_review=CLEAR. Separately authorize inventory/reconciliation before migration; never infer ownership from a single historical record or silently backfill. Resolve conflicts manually against authoritative payment evidence. No migrations executed.

Missing/mismatched retrieved customer_details.email preserves financial confirmation and sets identity review; comparison is trim/case-insensitive only. Intake identity is never overwritten. Assessment processing stays blocked pending separately approved operator reconciliation. No refunds implied. Session email is used for identity review; Customer-object linkage enrichment is not implemented and must be reviewed if a future flow begins reusing Customers.

Status GET requires the existing HttpOnly SameSite cookie containing a high-entropy submission capability; Assessment ID/query alone cannot authorize access. Output contains only coarse payment/processing states and fixed messages. Capability expires with existing cookie after 24 hours; no public lookup or new credential recovery channel added. Customer reload polls by refreshing; no payment confirmation from redirect. QA/completion/delivery are not implemented and never asserted.

Payment webhook and handoff stage lines are emitted in production as well as preview. Each line is a fixed event, stage, and allowlisted result or sanitized provider type and code. Bodies, secrets, and full email addresses are not logged.

Recovery: inspect sanitized payment/outbox/ownership/identity state under authorized tooling. A stored `or:stripe:review:<event>` can be re-evaluated with the authenticated replay in [review-replay.md](./review-replay.md). Do not clear the review key by hand. Do not retry active leases or backoff. For ambiguous remote acceptance, reconcile acknowledgement before replay; local keys cannot guarantee remote deduplication. Preserve original IDs. Never remove synthetic or consistency quarantine. Identity/ownership conflict resolution requires separate approval and evidence. No automatic new Checkout for expired Sessions; support intervention remains required. Retention/backups/access controls and real Redis/Stripe sandbox end-to-end verification remain owner prerequisites.
